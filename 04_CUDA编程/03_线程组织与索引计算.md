# 线程的组织方式

一次核函数启动会创建成千上万个线程，硬件按**网格（grid）→ 块（block）→ 线程（thread）**三级来组织它们，每一级都可以是三维的。

- **grid**：对应一次核函数启动的全部线程，内部按 block 划分；
- **block**：被调度到同一个 SM 上的一组线程，内部按 thread 划分，可以同步和共享内存；
- **thread**：最小执行单元，一个线程处理一份数据。

索引相关的内置变量一共四个，都是只读的：

| 变量 | 类型 | 含义 |
| --- | --- | --- |
| `threadIdx` | `uint3` | 当前线程在 block 内的编号 |
| `blockIdx` | `uint3` | 当前 block 在 grid 内的编号 |
| `blockDim` | `dim3` | 每个 block 的线程数（启动时指定） |
| `gridDim` | `dim3` | block 的总数（启动时指定） |

`uint3` 和 `dim3` 都有 `.x`、`.y`、`.z` 三个成员，区别是 `uint3` 只能读，`dim3` 可以在主机端构造和修改。

# 执行配置的写法

```c
dim3 block(16, 16);              // 每个 block 有 16x16 = 256 个线程
dim3 grid((w + 15) / 16, (h + 15) / 16);   // 覆盖 w x h 的网格

kernel<<<grid, block>>>(...);
```

只用到一维时可以直接写整数，`<<<grid, block>>>` 会被自动转换成 `dim3(grid, 1, 1)`。

几个由硬件固定的限制，超出会启动失败：

- **每个 block 最多 1024 个线程**，注意这是三个维度的乘积，不是某一维；
- 每个维度的取值范围：`x` 最大 2³¹−1，`y`、`z` 最大 65535；
- 不同的 CC 版本单卡可驻留的 block 数、线程数不同，代码里不要写死。

# 一维全局索引

最常用的公式，每个 CUDA 程序都会写：

```c
int i = blockIdx.x * blockDim.x + threadIdx.x;
```

含义是：前面所有 block 的线程总数加上当前线程在本 block 内的偏移。
这里的计算顺序不能反：`blockDim.x` 是每块宽度，`blockIdx.x` 是第几块。

配合总长度做边界保护：

```c
__global__ void vec_add(const float *a, const float *b, float *c, int n)
{
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n)                // 最后一个 block 通常不满，必须判断
        c[i] = a[i] + b[i];
}
```

为什么必须判断：grid 大小是用向上取整算出来的 `(n + block - 1) / block`，当 `n` 不是 `block` 的整数倍时，最后一个 block 里会有多余线程。**去掉这个 `if` 就是显存越界，而且不一定立刻崩溃**，可能只是悄悄改坏别的数据。

同理，`n` 很大时要留意 `int` 溢出。元素数超过 2³¹ 时应改用 `size_t` 或 `long long` 计算索引：

```c
size_t i = (size_t)blockIdx.x * blockDim.x + threadIdx.x;
```

# 二维索引

处理图像、矩阵这类二维数据时，用二维的 block 和 grid 更自然：

```c
__global__ void mat_add(const float *a, const float *b, float *c, int rows, int cols)
{
    int col = blockIdx.x * blockDim.x + threadIdx.x;   // x 方向对应列
    int row = blockIdx.y * blockDim.y + threadIdx.y;   // y 方向对应行
    if (row < rows && col < cols)
        c[row * cols + col] = a[row * cols + col] + b[row * cols + col];
}
```

两条约定要记清：

- **`x` 是变化最快的维度。** 同一个 warp 内连续编号的线程，`threadIdx.x` 连续递增，它们访问的内存地址才连续，才能形成合并访问。所以让 `x` 对应数组的行内下标（列），`y` 对应行号。
- **二维数组在设备内存里依然是线性存放的**，需要自己用 `row * cols + col` 换算成一维偏移。核函数里不能写 `a[row][col]`，除非传的是行指针数组。

如果把 `x` 和 `y` 写反（`x` 对应行、`y` 对应列），程序结果依然正确，但相邻线程访问的地址间隔了一整行，**带宽可能掉到原来的十分之一**，这是二维程序最常见的性能坑。

# 块大小怎么定

块大小（`blockDim`）的选择在入门阶段可以按下面的经验来：

- **取 32 的整数倍**。warp 是 32 个线程，不是 32 的倍数会浪费最后一个 warp 的执行槽位。
- **常用 128 或 256**。这两个值在大多数架构上能取得较好的占用率，且不容易因寄存器用量超限而降低并发 block 数。
- **不要用 1024**。虽然合法，但一个 block 占满 SM 的线程额度，一旦寄存器或共享内存稍有需求，SM 上就只能驻留一个 block，反而降低了延迟隐藏能力。
- 二维情况下常用 `dim3(16, 16)` 或 `dim3(32, 8)`，乘积仍是 256。

grid 大小则永远由数据规模反推：

```c
int block = 256;
int grid  = (n + block - 1) / block;   // 向上取整，保证覆盖全部元素
```

# 数据规模与线程数量的关系

**线程数不需要等于元素数，而是"覆盖"元素数。**

- 线程数略多于元素数（向上取整造成）→ 用 `if (i < n)` 过滤；
- 线程数少于元素数 → 每个线程用循环处理多个元素，这叫做**网格跨步循环（grid-stride loop）**：

```c
__global__ void vec_add(const float *a, const float *b, float *c, int n)
{
    for (int i = blockIdx.x * blockDim.x + threadIdx.x;
         i < n;
         i += blockDim.x * gridDim.x)
    {
        c[i] = a[i] + b[i];
    }
}
```

跨步循环的好处是**线程总数与数据规模解耦**，可以把 grid 固定成一个和显卡规模匹配的值，换成更大的输入也不用重新计算网格，还能避免超长 grid 的调度开销。数据量不确定或需要反复启动时，这种写法更稳妥。

# 索引计算的两个检查点

写完核函数后按这两条自查：

1. **每个数组访问都在 `if` 的边界保护之内**，包括所有 `a[i]`、`b[i]`、`c[i]`；
2. **索引用的是 `blockIdx.x * blockDim.x + threadIdx.x` 这个顺序**，而不是 `threadIdx.x * gridDim.x + blockIdx.x` 之类的直觉写法。
