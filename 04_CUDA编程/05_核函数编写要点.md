# 函数的三种修饰符

CUDA 用修饰符区分一个函数能在哪里定义、在哪里调用，这是主机与设备代码分界的第一个落点。

| 修饰符 | 在哪执行 | 谁能调用 |
| --- | --- | --- |
| `__global__` | 设备 | 主机调用（也可被设备调用，需动态并行） |
| `__device__` | 设备 | 只能被设备代码调用 |
| `__host__` | 主机 | 只能被主机代码调用（缺省值） |

```c
__global__ void kernel(int *p) { ... }      // 核函数，必须返回 void
__device__ int  square(int x) { return x * x; }   // 设备端工具函数
__host__ __device__ int add(int a, int b) { return a + b; }  // 两边都能用
```

几点必须记住的限制：

- **`__global__` 函数必须返回 `void`**，需要返回多个值时通过指针参数回写。
- **`__device__` 函数默认被内联**，递归调用需要开 `-rdc=true` 并显式指定 `-arch`，而且有额外开销，入门阶段直接避免递归。
- **`__host__ __device__` 双修饰常用在工具函数上**，比如取绝对值、比较大小，避免在两边各写一份。
- 设备代码里**不能调用标准库的阻塞函数**，如 `printf` 之外的大多数 `stdio`、`malloc`、`throw`。`printf` 在核函数里可用，但会强制串行化且有缓冲区限制，只用于调试。
- 设备代码里**不能访问静态局部变量和全局变量**（除 `__device__` 和 `__constant__` 修饰的），因为它们没有对应的设备端存储。

# 核函数里的变量

核函数内部声明的普通变量，默认放在**寄存器**里，每个线程一份，互不干扰。这是设备端最正常的存储方式，速度最快。

需要注意的三种情况会让变量"掉出"寄存器：

- **运行时不定的数组下标**：`float t[8]; t[k] = ...`，编译器无法把它放进寄存器，会放到本地内存。解决方法是把数组长度写成编译期常量并展开循环。
- **寄存器压力过大**：一个线程用了太多寄存器，SM 上的并发线程数就会下降。用 `--ptxas-options=-v` 可以看到每个线程用了多少寄存器。
- **超过硬件上限**：单线程可用的寄存器数有上限（通常 255 个 32 位寄存器），超出部分一律溢出到本地内存。

# 线程同步

同一个 block 内的线程可以互相等待，用的是 `__syncthreads()`：

```c
__global__ void kernel(float *data)
{
    __shared__ float s[256];
    int tid = threadIdx.x;

    s[tid] = data[tid];      // 各线程先写共享内存
    __syncthreads();         // 等所有线程都写完
    float v = s[255 - tid];  // 再读别人写的数据
}
```

关键点：

- **`__syncthreads()` 是 block 内的屏障**，不是整个 grid。不同 block 之间没有任何同步手段，跨 block 的协作只能通过"分成两个核函数"或原子操作来完成。
- **调用点必须能被 block 内所有线程到达**。写在 `if (tid < n)` 里面，而实际有线程不满足条件时，那些线程不会到达屏障，整个 block 会挂死。
- 它同时起到**内存屏障**的作用：屏障之前的写操作，对屏障之后的所有线程都可见。所以共享内存的读写必须靠它来保证正确性。
- 只靠它"顺便"做性能优化是不够的，它会让 warp 等待，调用次数越少越好。

# 原子操作

多个线程对同一地址做"读—改—写"时，普通的 `+=` 会产生竞争：

```c
count[0] += 1;      // 危险：两个线程可能同时读到旧值
```

CUDA 提供原子函数，保证这一步不可分割：

```c
atomicAdd(&count[0], 1);
atomicMax(&max_val, v);
atomicCAS(&lock, 0, 1);     // 比较并交换，可实现自旋锁
```

```c
int atomicAdd(int *address, int val);            // 原型之一
float atomicAdd(float *address, float val);      // 浮点版本需要 CC 2.0 以上
```

注意事项：

- **原子操作作用在全局内存或共享内存上**，对同一个地址的高频原子操作会成为性能瓶颈，因为它是串行化的。
- 原子操作**不保证执行顺序**，只保证不丢失更新。多次运行结果的累加顺序可能不同，浮点求和的末位可能因此变化。
- 典型的规约写法是"先在 block 内用共享内存两两归并，最后每个 block 只做一次 `atomicAdd`"，把几万次原子操作压到几十次。
- 早期架构只有整型原子操作，浮点原子操作是后续加入的；`double` 的 `atomicAdd` 需要 CC 6.0 以上。

# 线程发散

前面提过 warp 的执行方式，这里给出具体的判断方法。

```c
// 发散：warp 内的线程分成两半，两条路径都要执行
if (threadIdx.x % 2 == 0) { ... } else { ... }

// 不发散：条件在整个 warp 内取值相同
if (blockIdx.x == 0) { ... }
```

判断标准是**条件是否会在一个 warp 的 32 个连续线程中取到不同值**。所以：

- 依赖 `threadIdx.x` 的奇偶、大小比较，通常会造成发散；
- 依赖 `blockIdx` 的条件对整个 block 一致，不会发散；
- 循环次数随线程编号变化（如三角形循环）会造成尾部发散。

发散本身不是错误，只是效率损失。**入门阶段不要为了消除发散而把代码写得难懂**，先保证正确，再在 profile 时确认它是不是瓶颈。

# 写完核函数后的自查清单

1. 每个线程是否只访问自己的那份数据？有没有数组越界？
2. 有没有用到 `__syncthreads()`，调用点是否所有线程都能到达？
3. 跨线程累加是否用了原子操作，还是在最后才归并？
4. 有没有在核函数里调用主机函数，或者解引用主机指针？
5. 输入输出参数是不是都用了设备指针？
6. 变量是否大量溢出到本地内存（看 `-v` 输出的寄存器与 local 用量）？
