# 用什么衡量性能

CUDA 程序的性能有两个不同层面的指标，混用会导致错误的优化方向：

- **核函数耗时**：只统计设备端计算的时间，用于比较算法的优劣；
- **端到端耗时**：包含内存分配、H2D 拷贝、核函数、D2H 拷贝、释放，是用户实际感受到的时间。

新手常犯的错是核函数从 10 ms 优化到 5 ms，但端到端从 12 ms 变成 11 ms——因为另外 6 ms 都在拷贝上。**先量端到端，确定瓶颈在哪一步，再决定优化对象。**

# 用 CUDA 事件计时

主机端的 `clock()` 或 `std::chrono` 只能测到核函数启动的异步开销，测不到真实执行时间。正确做法是用 CUDA 事件，它在设备端的任务流里打点：

```c
cudaEvent_t start, stop;
cudaEventCreate(&start);
cudaEventCreate(&stop);

cudaEventRecord(start);
kernel<<<grid, block>>>(d_in, d_out, n);
cudaEventRecord(stop);

cudaEventSynchronize(stop);        // 等 stop 事件真正发生
float ms = 0.0f;
cudaEventElapsedTime(&ms, start, stop);
printf("kernel time: %.3f ms\n", ms);

cudaEventDestroy(start);
cudaEventDestroy(stop);
```

计时要注意三点：

- **`cudaEventSynchronize` 不能省**，否则 `stop` 还没发生就去读时间，得到的是 0 或垃圾值。
- **要重复多次取平均**。第一次启动包含上下文初始化、JIT 编译、缓存预热，通常明显偏慢，应作为预热跑掉不计入。
- 计时区间之间不要夹 `printf` 等主机操作，会引入额外等待。

# 有效带宽：判断优化是否到位

显卡的显存带宽是硬指标，用它算出的**有效带宽**可以和理论峰值对比，从而判断一段访存密集型代码还有多少优化空间：

```text
有效带宽 (GB/s) = 总访存量 (bytes) / 耗时 (s) / 1e9
```

以数组相加为例，每个元素读两次写一次，`n` 个 `float`：

```c
double bytes = 3.0 * n * sizeof(float);       // 2 读 + 1 写
double gbps  = bytes / (ms * 1e-3) / 1e9;
printf("effective bandwidth: %.1f GB/s\n", gbps);
```

如果算出的数值接近显卡理论带宽的 70%~80%，说明这段代码已经吃满了显存带宽，**再怎么改核函数也不会更快**，要继续提速只能减少访存量或改变算法。如果只有 20%，那大概率是访问模式不合并或者有本地内存溢出。

# 合并访问

这是访存优化里收益最大的一条。

一个 warp 的 32 个线程执行同一条访存指令时，硬件会把这些访问合并成尽可能少的内存事务：

- **相邻线程访问相邻地址**（步长为 1 个元素）→ 32 个 `float` 正好覆盖 128 字节，合并成 1 次事务；
- **相邻线程访问的地址间隔很大**（比如间隔一整行）→ 每个线程各占一次事务，带宽直接掉到 1/32。

```c
// 好：连续线程读连续地址
c[i] = a[i] + b[i];

// 坏：连续线程读同一列，地址间隔 cols
c[row * cols + col] = a[col * rows + row];
```

矩阵转置是最典型的场景。直接在原址上按转置方式读写，必然有一边是不合并的。标准做法是**用共享内存做中转**：先按合并方式读入共享内存，`__syncthreads()`，再按合并方式从共享内存写出，让不合并发生在片上而不是显存上。

结构体数组（AoS）也常导致问题：

```c
struct Particle { float x, y, z, w; };
// 差：一个线程读一个结构体，warp 的访问跨度为 16 字节，浪费 3/4 带宽
// 好：拆成 SoA，x[]、y[]、z[]、w[] 各一个数组，各自都是连续访问
```

# 占用率（Occupancy）

占用率衡量的是 **SM 上实际驻留的活跃 warp 数占硬件上限的比例**，它反映的是"有没有足够的线程来掩盖内存延迟"。

```text
占用率 = 每 SM 实际活跃 warp 数 / 每 SM 支持的最大 warp 数
```

以某代架构为例：每 SM 最多 2048 个线程（64 个 warp）、65536 个寄存器、96 KB 共享内存。那么每个 block 的资源需求会同时约束能驻留几个 block：

```text
驻留 block 数 = min( 2048 / blockDim,
                    65536 / (blockDim × 每线程寄存器数),
                    共享内存上限 / 每 block 共享内存 )
```

三项取最小值，再受硬件的 block 数上限约束（通常 16 或 32 个）。

所以三种情况会压低占用率：

- **寄存器用得太多**：每线程 64 个寄存器时，一个 SM 最多只能驻留 1024 个线程，占用率顶到 50%；
- **共享内存用得太多**：`TILE = 32` 的两个 `float` 块就占 8 KB，限制驻留 block 数；
- **block 太小或太大**：太小则 block 数上限先到，太大则单块占满 SM 的线程额度。

查看方式：

```bash
nvcc kernel.cu -o k --ptxas-options=-v     # 看每线程寄存器数、共享内存、本地内存
```

也可以在代码里限制：

```c
__global__ void __launch_bounds__(256, 4) kernel(...);   // 声明最多 256 线程/块、至少 4 块/SM
```

编译器会据此调整寄存器分配，可能牺牲单线程性能来换取更高的并发度。

**但占用率不是越高越好。** 有的计算密集核函数在 25% 占用率下就已经跑满算力，因为延迟被计算本身掩盖了。判断依据只能是实测：改变 block 大小或 `__launch_bounds__`，看耗时是否变化。**当占用率从 50% 提到 100% 而耗时不变时，说明瓶颈不在延迟隐藏上。**

# 专业的分析工具

- **Nsight Compute（`ncu`）**：逐个核函数分析，给出访存效率、占用率、各流水线利用率、瓶颈定位（memory bound / compute bound / latency bound）。
- **Nsight Systems（`nsys`）**：时间线视角，看主机与设备的重叠、拷贝与计算的比例、多个流的并行情况。

```bash
ncu --set full ./app                 # 完整指标，会多次重放核函数，很慢
ncu --metrics gpu__time_duration,sm__throughput.avg.pct_of_peak_sustained_elapsed ./app
nsys profile -o report ./app         # 生成时间线报告
```

入门阶段先学会看两个数就够了：**核函数的有效带宽**，和**时间线里拷贝/计算各占多少**。

# 优化的顺序

按投入产出比排，不要一上来就抠指令级细节：

1. **减少数据搬运**。能在设备上算完的不要在中间搬回主机；能合并成一次大拷贝的不要拆成多次小拷贝。
2. **让访存合并**。检查索引公式，保证 `threadIdx.x` 对应最内层连续维度。
3. **消除本地内存溢出**。检查 `-v` 输出里的 local memory 用量，把运行时数组下标改成常量。
4. **用共享内存消除重复的全局访问**。
5. **调 block 大小、`__launch_bounds__` 调占用率**。
6. **消除热点处的线程发散和原子操作竞争**。
7. 前面都做完还不够，才考虑用 `float4` 向量化访问、指令级并行、`__ldg`/只读缓存等手段。

每一次改动都要重新计时，**没有测量支撑的优化都是猜**。

# 一个容易忽略的坑

核函数里出现 `if (i < n)` 这种边界判断时，最后一个 block 的有效线程数很少，但整个 block 的资源照样被占用。数据量不是 block 大小整数倍时，尾部效率损失不可避免，但可以通过**减小 block 大小**或**用跨步循环让所有线程都干活**来摊薄。当数据量只有几万元素时，这点损失可能就占了总耗时的很大一块。
