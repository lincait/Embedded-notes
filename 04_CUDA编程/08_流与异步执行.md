# 主机与设备的异步关系

CUDA 的 API 分两类，混淆这两类是初学者写出"看起来更快但结果错"的程序的根源：

- **核函数启动是异步的**。`kernel<<<>>>` 只是把任务排进设备队列就立刻返回，主机继续往下走；
- **`cudaMemcpy` 是同步的**。函数返回时数据已经搬完，主机这段时间被阻塞。

所以下面这段代码是安全的：

```c
kernel<<<grid, block>>>(d_in, d_out, n);
cudaMemcpy(h_out, d_out, bytes, cudaMemcpyDeviceToHost);   // 会等核函数跑完
```

而下面这段是危险的：

```c
kernel<<<grid, block>>>(d_in, d_out, n);
printf("%f\n", h_out[0]);        // 错：主机上的数据还没被更新
```

设备上的任务全部排在**流（stream）**里，流就是一条按顺序执行的任务队列。上面第一种写法之所以安全，是因为 `cudaMemcpy` 默认在同一个流（默认流）里排在核函数之后，同一个流内的任务严格按顺序执行。

# 同步的三种方式

```c
cudaDeviceSynchronize();      // 等设备上所有流的任务全部完成，最重
cudaStreamSynchronize(s);     // 等某个流完成，粒度合适
cudaEventSynchronize(e);      // 等某个事件（即流中某个位置）完成，最轻
cudaDeviceReset();            // 销毁上下文，调试用，会释放所有资源
```

原则是**能用事件就不用流，能用流就不用设备**。`cudaDeviceSynchronize` 会把所有并行的流串起来，用多了等于放弃并发。

# 异步拷贝与固定内存

想要让拷贝不阻塞主机，用 `cudaMemcpyAsync`：

```c
cudaMemcpyAsync(d_a, h_a, bytes, cudaMemcpyHostToDevice, stream);
cudaMemcpyAsync(h_c, d_c, bytes, cudaMemcpyDeviceToHost, stream);
```

它有一个硬性前提：**主机端的缓冲区必须是固定内存（pinned memory）**，否则调用会退化成同步行为，甚至直接报错。

```c
cudaMallocHost(&h_a, bytes);      // 固定内存
// ...
cudaFreeHost(h_a);
```

原因在机制上：普通 `malloc` 的内存页可能被操作系统换出或移动，DMA 引擎无法在传输过程中处理这种情况，所以驱动只能先复制到内部固定缓冲区——这一步必须等主机参与，异步就退化了。固定内存物理页固定，DMA 可以直接读，主机才能在这段时间里去干别的事。

# 流的创建与使用

```c
cudaStream_t s1, s2;
cudaStreamCreate(&s1);
cudaStreamCreate(&s2);

kernel<<<grid, block, 0, s1>>>(...);        // 第四个执行配置参数指定流
kernel<<<grid, block, 0, s2>>>(...);

cudaStreamSynchronize(s1);
cudaStreamDestroy(s1);
cudaStreamDestroy(s2);
```

执行配置的四个参数到这里就全用上了：`<<<grid, block, sharedBytes, stream>>>`。

- **同一个流内的任务严格串行**，先后顺序由代码顺序决定；
- **不同流之间没有顺序保证，可以并发执行**，具体谁先谁后由硬件调度决定；
- 流不是越多越好。并发数受 SM 资源和拷贝引擎数量的限制，通常 2~4 个流就能获得大部分收益，开几十个流只会增加调度开销。

# 用多流重叠拷贝与计算

设备上的两个引擎是独立的：**拷贝引擎负责 H2D / D2H，计算引擎负责核函数。** 把数据切成互不相关的若干块、分给不同流，就能让"第 1 块的传输"和"第 2 块的计算"同时进行。

```c
const int NS = 4;
cudaStream_t s[NS];
for (int i = 0; i < NS; i++)
    cudaStreamCreate(&s[i]);

int chunk = (n + NS - 1) / NS;
for (int i = 0; i < NS; i++) {
    int off = i * chunk;
    int cnt = min(chunk, n - off);
    size_t b = cnt * sizeof(float);

    // 同一流内的三件事按顺序执行；不同流的同类操作可以并发
    cudaMemcpyAsync(d_a + off, h_a + off, b, cudaMemcpyHostToDevice, s[i]);
    kernel<<<(cnt + 255) / 256, 256, 0, s[i]>>>(d_a + off, d_c + off, cnt);
    cudaMemcpyAsync(h_c + off, d_c + off, b, cudaMemcpyDeviceToHost, s[i]);
}

cudaDeviceSynchronize();      // 最后统一等全部完成
```

这段代码的理论耗时接近 `总拷贝时间 + 单块计算时间`，而不是两者相加。前提是 `h_a`、`h_c` 都是固定内存，且各块之间确实没有依赖。

**如果数据不能分块（后一块的计算依赖前一块的结果），多流就帮不上忙**，只能拿到不同请求之间并发的收益。

# 用事件做跨流依赖

流之间默认无序，需要确定的先后关系时用事件：

```c
cudaEvent_t ev;
cudaEventCreate(&ev);                  // 如果只用于同步，可加 cudaEventDisableTiming 省开销

kernel_a<<<grid, block, 0, s1>>>(...); // 在 s1 里跑
cudaEventRecord(ev, s1);               // 在 s1 的这个位置打点

cudaStreamWaitEvent(s2, ev, 0);        // s2 等到这个点之后才开始后续任务
kernel_b<<<grid, block, 0, s2>>>(...); // 一定在 kernel_a 之后执行

cudaStreamDestroy(s1); cudaStreamDestroy(s2);
cudaEventDestroy(ev);
```

`cudaStreamWaitEvent` 只建立依赖，**不会阻塞主机**，这是它比 `cudaStreamSynchronize` 更适合做流水线编排的原因。

# 默认流的隐式同步

一个容易被"多流优化"坑到的地方：**传统的默认流（legacy default stream）会和所有其它流发生隐式同步**。

具体表现是：默认流里的操作要等其它所有流之前的任务完成才能开始，而其它流的操作也要等默认流之前的任务完成。结果是你写了多个流，实际却串行执行了，而且没有任何报错。

两种规避方式：

- **不要用默认流**。凡是参与并发的操作都显式指定流。
- **用非阻塞流**：

```c
cudaStreamCreateWithFlags(&s, cudaStreamNonBlocking);   // 不与默认流隐式同步
```

也可以用编译选项把默认流改成"每线程默认流"语义：

```bash
nvcc prog.cu -o prog --default-stream per-thread
```

改了之后，每个主机线程有自己的默认流，隐式同步消失——**但这也意味着原来依赖隐式同步保证顺序的代码可能出错**。这个选项只应在明确理解影响时使用。

# 初学者最容易犯的三个顺序错误

1. **在异步拷贝之后立刻读主机数据**。`cudaMemcpyAsync` 之后必须有 `cudaStreamSynchronize` 或 `cudaMemcpy`（同步版）才能读。
2. **用 `cudaMemcpy` 却期望它与计算重叠**。同步拷贝会阻塞主机，也占着默认流，多流重叠直接失效。要么全用 `Async` 版本，要么放弃重叠。
3. **在核函数里 `printf` 调试后忘了它会影响时序**。设备端的 `printf` 会强制刷新缓冲区，把异步的流水打乱，测出来的时间不可信。
