# I/O 多路复用基础

前面的 TCP 服务端可以为每个客户端创建一个进程或线程，但连接数量增加后，创建任务、线程栈和上下文切换都会带来明显开销。I/O 多路复用允许一个线程同时等待多个文件描述符的就绪事件。就是让一个进程或线程能够同时等待很多个 I/O 事件，哪个就绪了就处理哪个，而不是为每个连接创建一个线程去阻塞等待。

# I/O 多路复用解决什么问题

阻塞式 `recv()` 在没有数据时会让当前线程睡眠。如果一个线程顺序对多个客户端调用阻塞 `recv()`，它会卡在第一个暂时无数据的连接上，后面的连接即使已经有数据也得不到处理。

I/O 多路复用把“等待哪个描述符可以操作”交给内核：

1. 程序注册或提交一组文件描述符及关注的事件。
2. 线程阻塞等待，期间不占用 CPU 空转。
3. 内核发现一个或多个描述符就绪后唤醒线程。
4. 程序只对就绪描述符执行 `accept`、`recv`、`send` 等操作。
5. 处理结束后再次进入等待。

这里的“多路”是多个 I/O 对象，“复用”是复用一个等待线程。它不代表多个 I/O 操作在用户代码中自动并行，也不会替程序完成数据读写。

# 就绪不等于完成

I/O 多路复用报告的是**就绪状态**：此时执行某类操作通常不会因等待数据而阻塞。

- 监听套接字可读：至少有连接可以 `accept`，或者发生错误。
- TCP 连接可读：可能有数据、收到 FIN，或者存在待处理错误。
- 套接字可写：发送缓冲区有可用空间，不代表一整条消息必然一次发送完。

因此事件循环仍然必须检查系统调用的返回值。`recv()` 返回 `0` 表示对端关闭写方向；返回 `-1` 时要区分 `EINTR`、`EAGAIN` 和真正错误。

# select

`select` 使用三个 `fd_set` 分别关注可读、可写和异常事件：

```c
#include <sys/select.h>

int select(int nfds,
           fd_set *readfds,
           fd_set *writefds,
           fd_set *exceptfds,
           struct timeval *timeout);
```

使用时通过 `FD_ZERO`、`FD_SET`、`FD_ISSET` 操作集合，`nfds` 要传入最大文件描述符加 1。

`select` 的主要特点：

- 接口跨平台、历史悠久，适合描述符较少的程序；
- 文件描述符编号受 `FD_SETSIZE` 限制；
- 每次调用前都要重新准备集合，因为内核会修改传入的集合；
- 返回后需要从头扫描集合找出就绪描述符，数量大时开销明显。

超时参数为 `NULL` 表示一直等待，零时间表示立即返回。超时值也可能被修改，循环中不能假定它保持不变。

# poll

`poll` 使用 `struct pollfd` 数组描述每个文件描述符及其事件：

```c
#include <poll.h>

struct pollfd {
    int   fd;
    short events;
    short revents;
};

int poll(struct pollfd *fds, nfds_t nfds, int timeout);
```

`events` 是程序关注的事件，`revents` 由内核填写实际发生的事件。常见事件包括 `POLLIN`、`POLLOUT`、`POLLERR` 和 `POLLHUP`。

与 `select` 相比，`poll` 没有 `fd_set` 的固定编号上限，数组也更容易动态管理。但每次调用仍要把描述符数组交给内核，返回后仍需线性扫描所有元素，因此连接很多而就绪连接很少时效率不理想。

# epoll

`epoll` 是 Linux 特有的 I/O 多路复用接口。程序先创建 epoll 实例，再用 `epoll_ctl` 维护长期存在于内核中的**关注列表**；`epoll_wait` 只返回已经就绪的事件。

与每次提交完整集合的 `select`、`poll` 相比，epoll 不需要在每轮等待时重新传递全部描述符，也不用扫描所有未就绪连接，因此更适合大量连接、少量连接同时活跃的服务器。

但“epoll 一定更快”也不准确：描述符很少、逻辑简单时，`select` 或 `poll` 的代码可能更直接；真正的性能还取决于事件处理、内存分配、锁竞争和业务逻辑。

# 三种机制的对比

| 对比项 | select | poll | epoll |
| --- | --- | --- | --- |
| 平台 | POSIX，兼容性好 | POSIX，兼容性好 | Linux 特有 |
| 描述方式 | 位集合 | `pollfd` 数组 | 内核中的关注列表 |
| 数量限制 | 受 `FD_SETSIZE` 影响 | 主要受进程 fd 上限影响 | 主要受进程 fd 上限影响 |
| 每轮提交 | 重新提交集合 | 重新提交数组 | 只提交增删改 |
| 查找就绪项 | 线性扫描 | 线性扫描 | 返回就绪事件数组 |
| 触发模式 | 水平触发 | 水平触发 | 水平触发或边沿触发 |

# 水平触发与边沿触发

epoll 支持两种通知方式：

- **水平触发（LT）**：默认模式。只要描述符仍处于就绪状态，后续 `epoll_wait` 还会继续报告。
- **边沿触发（ET）**：只在状态从未就绪变为就绪时通知。若一次没有处理干净，内核可能不会为剩余数据再次通知。

ET 模式通常要配合非阻塞 I/O，并循环读取或写入，直到返回 `EAGAIN`/`EWOULDBLOCK`。LT 更容易写对，学习和普通服务器应先使用 LT，确实需要降低重复通知开销时再考虑 ET。

# 典型事件循环

网络服务器的结构通常是：

```text
创建监听套接字并 bind、listen
        ↓
把监听 fd 加入多路复用机制
        ↓
等待就绪事件
        ↓
监听 fd 就绪？──是──> accept 新连接并注册连接 fd，同时将其加入多路复用
        │
        否
        ↓
连接 fd 就绪──> recv/send，关闭断开或出错的连接
        ↓
回到等待
```

事件循环把“接受新连接”和“处理已有连接”放在同一个线程中调度。业务处理时间必须足够短，否则某个连接中的耗时任务会阻塞整个循环。CPU 密集计算、慢速数据库操作等工作通常要交给线程池、进程池或异步任务系统。

# 非阻塞 I/O

可用 `fcntl` 把文件描述符设置为非阻塞：

```c
#include <fcntl.h>

int flags = fcntl(fd, F_GETFL, 0);
if (flags != -1) {
    fcntl(fd, F_SETFL, flags | O_NONBLOCK);
}
```

非阻塞模式下，暂时不能完成的操作不会让线程睡眠，而是立即返回 `-1`，并把 `errno` 设为 `EAGAIN` 或 `EWOULDBLOCK`。这不是连接错误，只表示当前数据已经处理完或缓冲区暂时没有空间。

不要用非阻塞轮询代替多路复用：如果程序不停对所有 fd 调用 `recv`，仍会浪费 CPU。正确组合是由 `select`、`poll` 或 `epoll` 等待事件，再对就绪 fd 执行非阻塞操作。

# 常见事件与处理原则

- **可读事件**：循环读取并正确处理返回值 `0`、`EINTR` 和 `EAGAIN`。
- **可写事件**：只在存在尚未发送的数据时关注；套接字通常长期可写，始终监听会导致事件循环频繁唤醒。
- **挂断和错误**：获取并记录错误，注销描述符后关闭资源。
- **超时**：多路复用等待超时不等于故障，可用于执行定时检查。

同一个 fd 被关闭后，其整数编号可能很快被新文件复用。事件管理代码要及时从关注集合移除旧连接，并避免把旧连接状态错误地套用到新 fd。

# 适用范围与限制

I/O 多路复用适合大量套接字、管道、终端等“等待时间长、单次处理短”的 I/O。普通磁盘文件在 `select`、`poll` 中通常总被视为就绪，而 epoll 一般不接受普通文件，因此这些接口不能提供真正的异步磁盘 I/O。

单线程事件循环减少了线程数量和同步问题，但仍需维护每个连接的接收缓冲区、发送进度和协议状态。连接数量越多，状态管理越重要，代码并不会因为使用 epoll 自动变简单。

# 小结

- I/O 多路复用让一个线程等待多个文件描述符，返回的是就绪事件，不会自动完成 I/O。
- `select`、`poll` 每轮都处理完整集合；epoll 在内核维护关注列表并返回就绪项。
- ET 模式必须配合非阻塞 I/O 并处理到 `EAGAIN`；LT 更容易正确使用。
- 事件循环不能执行长时间阻塞或计算密集任务，否则所有连接都会被拖慢。
