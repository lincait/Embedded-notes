# 守护进程

守护进程（daemon）是在后台长期运行、通常不与用户终端直接交互的进程。网络服务、日志服务、定时任务和设备管理程序都可能采用这种运行方式。

“在命令末尾加 `&`”只能让普通进程进入后台，并不等于完成守护进程化。传统守护进程还需要脱离原会话和控制终端、处理继承的文件描述符，并建立独立的日志与退出机制。

# 会话、进程组和控制终端

理解守护进程之前，先区分三个概念：

- **进程组**：一组相关进程的集合，用于作业控制和批量发送信号；进程组长的 PID 等于 PGID。
- **会话**：一个或多个进程组的集合；会话首进程的 PID 等于 SID。
- **控制终端**：与会话关联的终端，负责终端输入、输出以及 `Ctrl+C`、终端挂断等事件。

普通程序常由 Shell 启动，继承 Shell 所在的会话、进程组和控制终端。如果用户退出终端，相关程序可能收到 `SIGHUP`。守护进程通过创建新会话脱离原控制终端，使生命周期不再依赖某次登录会话。

可以使用 `ps` 查看这些关系：

```bash
ps -eo pid,ppid,pgid,sid,tty,stat,cmd
```

守护进程的 `TTY` 通常显示为 `?`，表示没有控制终端，但这只是观察结果，不是创建守护进程的全部条件。

# 传统守护进程的创建流程

## 第一次 fork：让父进程退出

第一次的目的是脱离原来的进程，设置一个新的会话。

父进程调用 `fork()`，随后退出；子进程继续执行。这样调用者可以及时返回，同时子进程通常不再是进程组长，为后续调用 `setsid()` 创造条件。

```c
pid_t pid = fork();
if (pid < 0) {
    return -1;
}
if (pid > 0) {
    _exit(0);  // 父进程退出，不刷新继承的 stdio 缓冲区
}
```

这里使用 `_exit`，是为了避免父子进程重复刷新 `fork` 前继承的标准 I/O 缓冲区。

## setsid：创建新会话

```c
pid_t setsid(void);
```

调用成功后，当前进程会成为新会话首进程和新进程组组长，并脱离原控制终端。若调用者已经是进程组长，`setsid()` 会失败，因此传统流程先执行一次 `fork()`。

## 第二次 fork：避免重新获得控制终端

第二次的目的是，避免在新会话中获得控制终端。

第一次 `fork` 后的子进程调用 `setsid()`，此时它成为会话首进程。某些系统规则下，会话首进程仍可能重新获得控制终端。再次 `fork()` 并让父进程退出后，留下的孙进程不再是会话首进程，从而避免这种情况。

第二次 `fork` 是经典的双重 fork 方案，但并非所有程序都必须照搬。若服务由 systemd 等服务管理器启动，通常应以前台方式运行，由管理器负责脱离终端、重启和日志收集。

## 设置工作目录和权限掩码

守护进程不应长期占用一个可能需要卸载的启动目录，传统做法是切换到根目录或明确的服务目录：

```c
if (chdir("/") == -1) {
    return -1;
}
```

`umask` 决定创建文件时会屏蔽哪些权限位：

```c
mode_t old_mask = umask(027);
```

不要机械地认为守护进程必须 `umask(0)`。清零掩码便于程序完全控制权限，但程序随后必须为每个文件指定安全模式。若无特殊需要，使用较严格的掩码更稳妥。

## 处理继承的文件描述符

`fork()` 会继承父进程打开的文件描述符。守护进程应关闭不再使用的描述符，否则可能导致文件、套接字或挂载点长期无法释放。

标准输入、输出和错误通常重定向到 `/dev/null`，避免后续代码意外使用 `0`、`1`、`2` 时访问无效描述符：

```c
#include <fcntl.h>
#include <unistd.h>

int nullfd = open("/dev/null", O_RDWR);
if (nullfd == -1) {
    return -1;
}

dup2(nullfd, STDIN_FILENO);
dup2(nullfd, STDOUT_FILENO);
dup2(nullfd, STDERR_FILENO);
if (nullfd > STDERR_FILENO) {
    close(nullfd);
}
```

程序可以用 `sysconf(_SC_OPEN_MAX)` 查询文件描述符上限，再关闭不需要的描述符；也可以在创建描述符时设置 `O_CLOEXEC` 或 `FD_CLOEXEC`，防止它们泄漏给之后执行的新程序。

# 使用 syslog 记录日志

守护进程没有终端，不能依赖 `printf` 输出运行信息。传统接口是 `openlog`、`syslog` 和 `closelog`：

```c
#include <syslog.h>

openlog("mydaemon", LOG_PID | LOG_NDELAY, LOG_DAEMON);
syslog(LOG_INFO, "service started, pid=%ld", (long)getpid());
syslog(LOG_ERR, "open config failed: %m");
closelog();
```

- `ident`：每条日志前使用的程序标识。
- `LOG_PID`：记录进程 PID。
- `facility`：日志来源类别，普通守护进程常用 `LOG_DAEMON`。
- `priority`：严重级别，常见的有 `LOG_ERR`、`LOG_WARNING`、`LOG_INFO`、`LOG_DEBUG`。
- `%m`：在 syslog 格式串中展开为当前 `errno` 对应的错误信息。

采用 systemd 的系统中，可以用下面的命令查看服务日志：

```bash
journalctl -u 服务名
journalctl -f
```

# 信号与优雅退出

长期运行的服务必须设计清晰的信号语义：

- `SIGTERM`：请求程序停止；应结束事件循环、关闭套接字、刷新状态并释放资源。
- `SIGHUP`：传统上用于通知服务重新加载配置，而不是简单忽略或直接退出。
- `SIGCHLD`：守护进程创建子进程时，需要回收退出的子进程。

信号处理函数中只能安全地执行很有限的操作。常见做法是只设置一个 `volatile sig_atomic_t` 标志，在主循环中检查并完成清理：

```c
#include <signal.h>

static volatile sig_atomic_t stop_requested = 0;

static void handle_term(int signo)
{
    (void)signo;
    stop_requested = 1;
}
```

注册处理函数时优先使用 `sigaction()`，不要在信号处理函数里直接调用 `printf`、`malloc` 等非异步信号安全函数。

# PID 文件与单实例运行

部分守护进程会把 PID 写入 `/run` 下的文件，便于管理工具定位进程。但“检查 PID 文件是否存在”不能可靠防止重复启动，因为旧文件可能残留，PID 也可能被复用。

若确实需要单实例运行，应打开 PID 文件并使用 `flock` 或 `fcntl` 加锁，让锁的生命周期跟随文件描述符；程序退出时锁会由内核释放。

# 守护进程与服务管理器

经典双重 fork 适合学习 UNIX 进程、会话和控制终端，但现代 Linux 服务通常交给 systemd、BusyBox init、runit 等服务管理器管理。由管理器启动时，程序一般应该：

- 保持前台运行，不自行双重 fork；
- 把日志写到标准输出、标准错误或系统日志；
- 正确响应 `SIGTERM`；
- 用退出码报告失败，由管理器负责重启和依赖关系。

对于嵌入式系统，要根据实际 init 系统选择方式。不要同时让程序自我守护、又要求服务管理器跟踪前台主进程，否则容易出现 PID 跟踪和重启判断错误。

# 小结

- 守护进程与控制终端和登录会话解耦，通常长期在后台提供服务。
- 传统流程包括 `fork`、`setsid`、可选的第二次 `fork`、设置目录和 `umask`、处理继承描述符。
- 后台服务应使用系统日志，并通过信号完成配置重载和优雅退出。
- 现代服务管理器下通常保持前台运行，不要无条件照搬双重 fork。
